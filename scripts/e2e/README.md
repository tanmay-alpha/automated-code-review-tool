# Real GitHub end-to-end harness

Requires Python 3.11 with `cryptography`, `psycopg2-binary`, and the ML worker's dependencies; Java 21; authenticated `gh` with `repo`/webhook permissions; `git`; and `cloudflared`. PostgreSQL and Redis must already be running. Windows defaults match the isolated local E2E services (Postgres 55432, Redis 56379). Override connection options as needed; passwords can come from `E2E_PG_PASSWORD` and `E2E_REDIS_PASSWORD`.

**Destructive:** each run drops/recreates the configured PostgreSQL database (`acrt` by default). Use only a disposable database and GitHub sandbox. The runner creates six empty commits (two per scenario) and requests three GitHub webhook redeliveries. It does not rebuild the jar or stop the pre-existing database/Redis processes.

From the repository root:

```powershell
python scripts/e2e/run_github_e2e.py --api-jar apps/api/target/automated-code-review-tool-api.jar --api-sha <built-git-sha> --worker-dir apps/ml-worker --repo tanmay-alpha/acrt-e2e-sandbox --reuse
```

Use the actual build revision for `--api-sha`; the report separately hashes the copied jar. The runner snapshots the jar into its unique `out/<UTC timestamp>/` directory before starting it. Add `--reuse` for an existing sandbox seeded with `examples/demo-repo/seed_demo_repo.py`; the database is still recreated. Before connecting, old quick-tunnel callbacks recorded in this harness's prior reports for the same sandbox are deleted and recorded as `staleHooksDeleted`. Unrelated hooks are untouched. Keep the old reports locally so their callbacks can be recognized. Existing comments are retained and recorded as a baseline, not deleted to manufacture passing assertions; use a fresh sandbox for an isolated baseline.

The user token is fetched from `gh auth token`, encrypted with the API's AES-256-GCM wire format, and upserted into `users`; access JWTs match `JwtService`'s HS256 claims (including `ver=0` for the recreated user's default `token_version`) and Base64 key handling. Bearer authentication does not depend on `__Host-` cookie names. All generated secrets stay in memory/process environments. Readiness uses HTTP polling, including an authenticated API request; `/actuator/health` is deliberately not used because the local Windows Redis INFO response breaks its health indicator. Pass `--python apps/ml-worker/.venv/Scripts/python.exe` when that worker environment exists; otherwise the default interpreter must have the dependencies above.

`report.json` and `report.md` record expected findings, line-specific decoys (including TypeScript comment/string/timeout decoys), initial summary count, real GitHub redelivery, and sticky-comment identity/body on a new PR head. `/api/reviews/{prId}/runs` must expose both heads with `published` publication status, comment URL, and full published SHA; the comment body displays the formatter's 12-character SHA. Readiness waits for publication, not only review processing. Duplicate webhooks intentionally receive an empty HTTP 200: unchanged durable delivery/run identities, attempt counts and completion timestamps prove the redelivery was ignored, alongside unchanged comment IDs throughout `--observe-seconds` (default 10). This is a bounded observation, not an unbounded-time guarantee. The unchanged Java SHA-256 decoy only proves diff-scope exclusion. Missing/failed reviews block detector checks rather than silently passing them. GitHub issue comments are paginated; OAuth-created summaries are identified by the exact `<!-- acrt:summary repo=<github id> pr=<number> -->` marker and author, not by `[bot]` account type. Existing marker-matching summaries are reused, not deleted.

The runner also waits for PostgreSQL `ml.ingestion_outbox` events to complete, records counts by status, and scans the API log for `ERROR` entries with separate OutboxProcessor, OutboxClaimService, SKIP LOCKED, and SQL error counts. Any API `ERROR` fails the run; retained sanitized error lines provide evidence rather than suppressing app defects.

Exit codes: `0` all assertions pass; `1` assertions fail or are blocked; `2` setup/infrastructure failure. A report is written even on setup failure. Service/tunnel PIDs and cleanup results are recorded, and process trees started by the harness are terminated on exit. Logs are sanitized before final evidence is saved. The repository is retained unless `--delete-repo`; deletion requires the separate `delete_repo` scope. If retained, the runner prints the manual deletion command. `out/` (including the jar snapshot and logs) is gitignored.
